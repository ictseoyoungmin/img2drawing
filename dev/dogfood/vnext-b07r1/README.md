# B07-R1 — canonical session growth: measurement and closure

## Trigger

A Claude dogfood run drew the sniper-girl croquis to completion just after B08 and
produced a **313,391-line** canonical session against the R23 baseline's **39,866**
(7.86x) — with head/hair quality that was, if anything, slightly worse.

The initial reading was that correction/inspection/residual bookkeeping had over-grown.
The measurement says otherwise.

## Where the 313,391 lines actually were

| layer | lines | share |
|---|---|---|
| `history.actions` | 309,221 | **98.7%** |
| `corrections` + `residuals` + `observations` + `inspection_history` + telemetry | ~4,100 | **1.3%** |

Compacting the bookkeeping — the original hypothesis — would have recovered 1.3%.

### The format was never the problem

| | R23 (Pn) | vNext (B08) |
|---|---|---|
| actions | 394 | 1,784 |
| **hand-authored strokes** | **394** | **386** |
| machine hatch-fill strokes | 0 | 1,398 |
| points per stroke | 3.7 | 21.0 |
| stored points | 1,462 | 37,498 |
| **lines per stored point** | **21.8** | **8.2** |

Per unit of geometry the vNext record is **2.6x more compact** than R23. The artistic
content was the same size in both. The file grew because the session stored 25.6x more
geometry.

### Why it stored 25.6x more geometry

1. **No fill primitive.** The renderer deposits far less than its opacity number
   suggests; the dogfood measured 372 hatch strokes moving a region's value from 228 to
   227. With no way to say "this garment is value 90", the agent brute-forced tone with
   1,398 hand-rolled hatch strokes.
2. **No guidance against sampling a straight line.** The agent's own hatch helper
   emitted a point every 4px along lines that needed two endpoints.
3. **`tool_state` was written twice per action** — once on the action, once inside the
   stroke payload, byte-identical. 69,619 lines, 22.2% of the file, pure duplication.
4. **Derived pressure was persisted.** `shaped_pressure_profile` is a pure function of
   the point count and the tool taper; storing its output recorded the renderer's
   arithmetic as if it were an authored decision. 40,999 lines.

Items 1 and 2 are guidance failures before they are agent failures: a surface that lets
an agent brute-force tone will be brute-forced.

## Fixes

- `core/fill.py` — `FillRegion` / `ReservedLight`, analytically clipped hatch. One
  authored action per tone region; straight runs stored as two endpoints.
- `region.fill` action kind, expanded deterministically on replay. Generated lines keep
  stable ids so `soft_lift` still addresses them individually.
- `render/tone_scale.py` + `data/tone_scale.json` — deposition calibrated **once**, out
  of session, regenerated by `dev/calibration/calibrate_tone_scale.py`. Agents ask for
  an observed value, not an opacity.
- Reserved lights: a light inside a dark mass is left in the paper by the fill rather
  than erased back out afterwards.
- `history.py` — `tool_state` written once; derived pressure recomputed on load.
  Explicitly authored pressure is still stored verbatim. Older sessions load unchanged.
- The erase-mode rejection now names the API to use instead.

## Result

Re-authoring the same value pass through `fill_region` (`run.py`):

| | B08 hand-hatched | B07-R1 `fill_region` |
|---|---|---|
| canonical actions for the value pass | 1,398 | **9** |
| rendered strokes | 1,398 | 508 |
| stored points | ~29,000 | **1,016** |
| session lines for the value pass | ~276,000 | **1,382** |

Rendered values land on target (jacket 119 vs 120, rifle 35 vs 35, boots 57 vs 50; sock
regions read ~15 lighter because their reserved rim lights raise the mean, as intended).

## Regression caught by this work

A two-point fill line initially rendered near-blank: `shaped_pressure_profile` spends a
short path entirely on its entry and exit taper, so a line with only two points never
reaches full pressure. Fill lines now carry the tool's constant pressure, which is also
what the calibration measures. `test_a_filled_region_renders_near_the_requested_value`
locks this down — a table that is right on paper and wrong on canvas is worse than no
table.

## Handoff note for B11

`region.fill` replays through `CanvasHistory.state_at`, so resume and undo/redo are
covered. Timelapse is still wired only to the legacy R23 `core.session.DrawingSession`;
when B11 brings vNext to timelapse parity it must decide how a fill frame reads — one
action deposits a whole value region at once, and the frame duration heuristic in
`provenance/timelapse.py` already reserves a longer hold for it.
