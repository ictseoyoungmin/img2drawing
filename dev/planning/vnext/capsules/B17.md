## Release-candidate identity

The current package is `0.6.0rc1`, release slice
`B17_package_public_api_release_candidate`, with public contract
`DrawingSession/0.6.0-vnext`. `_version.py` remains build metadata authority. R23 keeps
its frozen `DrawingRun/0.5.2-r23` identity only at `img2drawing.legacy.r23`; the historical
validator checks that preserved manifest under the current vNext package instead of
requiring the current package to impersonate R23.

## Lean artifact boundary

The wheel contains Python runtime modules, required JSON data, and LICENSE. The sdist
additionally contains `SKILL.md`, canonical stage-free references, and the two selected
mechanical examples. Maintainer-only support, migration, release, and contract-freeze
records live under `dev/release/vnext/` and do not ship in the skill or sdist.

The deployable skill also excludes dev/dogfood/raw evidence/temp data, legacy playbooks,
stage reference docs, stage-review leftovers, caches, detailed subject fixtures, answer
targets, and NOTICE. Historical versions remain available through Git history.

## Canonical integration examples

`examples/mechanical_workflows.py` owns shared deterministic mechanics. The observed
example creates its own synthetic reference; the subjectless example uses imaginative
authority and drawing-only inspection without a fake subject, overlay, or registration.
Both perform create, observe, draw, inspect, record a material residual, replace the
responsible stroke, re-inspect, resolve, finish, render PNG, export action replay/GIF,
resume, and verify current completion provenance. They are explicitly not quality claims.

## B17-R1 remote-environment hardening

The first B17/B18 push failed on GitHub Actions because the package verifier used
`python -m build --no-isolation` and a virtual environment with
`system_site_packages=True`. Those checks could depend on the ambient editable-development
environment and therefore did not prove the release-candidate boundary they claimed.

B17-R1 keeps the product/runtime contract unchanged and narrows the verifier instead:

- wheel/sdist are built through the declared isolated PEP 517 build environment;
- the install check creates a fresh venv with `system_site_packages=False` and its own pip;
- the built wheel is installed normally so its two runtime dependencies are resolved from
  wheel metadata inside that venv;
- NumPy and Pillow module paths are checked to live under the fresh venv; and
- captured subprocess output is emitted before a failing command is re-raised.

## Skill-surface cleanup

Release/control-plane records were moved to `dev/release/vnext/`. The skill root now keeps
only the operating spec, canonical references, deterministic examples, runtime source,
package metadata, README, and LICENSE. Legacy `playbooks/`, `references/stages/`, and the
stage-review documents already excluded from the sdist were removed from the source skill
as well so a raw copied skill and a built sdist expose the same canonical attention surface.

## Verification

- skill source/docs link audit: pass;
- isolated PEP 517 wheel/sdist build: required;
- wheel/sdist path, content, version, dependency, license, English-only guidance,
  local-link, absolute-path, secret-pattern, and traversal audit: required;
- truly isolated wheel install plus installed observed/subjectless examples: required;
- installed NumPy/Pillow must resolve from the fresh venv rather than host site-packages;
- release/control-plane and historical stage/playbook files must not leak into the skill or sdist;
- frozen R23 compatibility boundary remains explicit under `0.6.0rc1`.

## Reopen conditions

Reopen B17 if build/install/API/version truth diverges, artifacts include unapproved
evidence or control-plane paths, canonical docs route new work into R23/Pn, selected
examples bypass the installed package or fake reference evidence, dependencies/licenses
drift without audit, or CI stops exercising the release-candidate boundary.
